# ПР1. Інтеграція зовнішнього REST API

Матеріали до першої практичної роботи. Повний текст завдання, критерії приймання й контрольні запитання — у документі `ПР1.pdf`, виданому до заняття. Тут лежить те, що допомагає почати роботу й перевірити себе.

## Задача коротко

Веб-застосунок, який за назвою міста показує поточну погоду — температуру й швидкість вітру. Джерело даних — публічний REST API **Open-Meteo**, ключ доступу не потрібен. Бекенд на FastAPI, робота з API винесена в окремий модуль.

## Що в цій папці

| Файл | Призначення |
|---|---|
| `app/` | Каркас застосунку |
| `requirements.txt` | Залежності роботи |
| `check_env.py` | Перевірка середовища: версія Python, пакети, доступ до Open-Meteo |
| `samples/` | Реальні відповіді API, збережені як файли |

```
app/
├─ main.py                веб-рівень: сторінка і JSON-ендпоінт /api/weather
├─ weather.py             модуль інтеграції з API — заготовки функцій
└─ templates/index.html   сторінка з формою вводу міста
```

Каркас дає структуру проєкту й робочий веб-рівень, щоб ви не витрачали заняття на плумбінг. **Реалізації в ньому немає:** обидві функції в `weather.py` наразі підіймають `NotImplementedError`, а веб-ендпоінт не обробляє помилок. Саме це — ваша робота.

## Початок роботи

```bash
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
python check_env.py
```

Для macOS і Linux активація середовища — `source .venv/bin/activate`. Якщо перевірка показує `[ !! ]` навпроти доступу до мережі, розберіться з цим до початку роботи: інакше згодом ви будете шукати помилку у власному коді там, де її немає.

Запуск застосунку з папки `pr1`:

```bash
uvicorn app.main:app --reload
```

Далі відкрийте http://127.0.0.1:8000 — сторінка з формою вже працює, а от запит погоди завершиться помилкою, доки ви не реалізуєте модуль інтеграції.

## Що реалізувати

| Де | Що зробити |
|---|---|
| `app/weather.py` → `find_city` | Знайти координати міста за назвою; вирішити, що функція повертає і як поводиться, коли міста немає |
| `app/weather.py` → `get_current_weather` | Поєднати геокодування і запит прогнозу; віддати температуру й швидкість вітру або зрозумілу помилку |
| `app/weather.py` → `WeatherError` | Вирішити, чи достатньо одного типу помилки, чи їх треба розрізняти |
| `app/main.py` → `api_weather` | Спроєктувати обробку збоїв: який HTTP-статус відповідає якій помилці |
| `app/templates/index.html` | Показати результат у зрозумілому вигляді замість сирого JSON |

Рішення, які стоять за кожним пунктом, перелічені в розділі 4 практичної роботи — продумайте їх до того, як писати код.

## Точки входу API

- Геокодування (назва міста → координати): `https://geocoding-api.open-meteo.com/v1/search`
- Прогноз за координатами: `https://api.open-meteo.com/v1/forecast`

Які саме параметри передавати й у якому вигляді — дивіться в документації Open-Meteo: https://open-meteo.com/en/docs

## Зразки відповідей

У папці `samples/` — справжні відповіді сервісу, збережені під час підготовки роботи. Вони потрібні, щоб ви бачили реальну форму даних, могли перевірити розбір відповіді без звернення до мережі й підготували обробку неприємних випадків заздалегідь.

| Файл | Що це |
|---|---|
| `geocoding-kyiv.json` | Успішне геокодування: місто знайдено |
| `geocoding-not-found.json` | Місто не знайдено |
| `forecast-kyiv.json` | Успішний прогноз за координатами |
| `forecast-error-400.json` | Відповідь сервера на некоректний запит, статус `400` |

### На що звернути увагу в зразках

Три спостереження, які легко пропустити й дорого виправляти потім.

**Коли місто не знайдено, ключа `results` немає взагалі.** Порівняйте `geocoding-kyiv.json` і `geocoding-not-found.json`: у другому не порожній список, а відсутнє поле. Код, який очікує `results` і бере з нього перший елемент, на цьому впаде.

**Помилка приходить із тілом.** У `forecast-error-400.json` сервер разом зі статусом `400` повернув JSON із полем `reason`, де людською мовою написано, що не так із запитом. Це корисно для діагностики — але вирішіть свідомо, чи показувати такий текст користувачеві вашого застосунку.

**Координати у відповіді не ті, що в запиті.** Прогноз запитували для `50.45466, 30.5238`, а у `forecast-kyiv.json` повернулося `50.4375, 30.5`: сервіс прив'язує запит до вузла своєї сітки. Якщо десь звірятимете координати на точну рівність — не збігатимуться.

Зверніть увагу й на те, що поля `temperature_2m` та `wind_speed_10m` лежать усередині об'єкта `current`, а одиниці вимірювання — окремо, в `current_units`.

## Чекліст самоперевірки

Пройдіть його перед здаванням — він повторює критерії приймання.

- [ ] Параметри запиту передаються структуровано, URL не склеюється вручну.
- [ ] Кожен запит має обмеження часу (**timeout**).
- [ ] Оброблено недоступність сервісу, таймаут, коди `4xx` і `5xx`, несподіваний формат відповіді — застосунок не аварійно завершується.
- [ ] Оброблено випадок, коли місто не знайдено.
- [ ] Робота з API винесена в окремий модуль; веб-рівень не містить деталей HTTP-клієнта.
- [ ] Веб-ендпоінт повертає JSON при успіху й відповідний HTTP-статус при помилці.
- [ ] Сторінка показує погоду або зрозуміле повідомлення про помилку.
- [ ] Перевірено на кількох містах, на неіснуючому місті та на порожньому вводі.
- [ ] Ви можете пояснити кожне ухвалене рішення.
