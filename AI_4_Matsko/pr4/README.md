# ПР4. Керування контекстом і structured output

Матеріали до четвертої практичної роботи. Повний текст завдання, критерії приймання й контрольні запитання — у документі `ПР4.pdf`, виданому до заняття.

## Задача коротко

Помічник служби підтримки з ПР3 стає **діалоговим** і **придатним для програмної обробки**. Клієнт веде розмову з кількох повідомлень, і помічник враховує сказане раніше. Кожна його відповідь — не вільний текст, а структурований обʼєкт за схемою, яку ви спроєктуєте: текст для клієнта, тема звернення, чи відповідь ґрунтується на правилах, чи потрібне уточнення, чи передати оператору, номер замовлення. Відповідь перевіряється за схемою до того, як потрапить до веб-рівня; історія розмови вміщується в бюджет токенів.

Наприкінці — порівняння трьох конфігурацій (нечіткий запит, структурований prompt, context engineering) і класифікація помилок моделі.

## Що в цій папці

| Файл | Призначення |
|---|---|
| `app/` | Каркас застосунку |
| `requirements.txt` | Залежності роботи |
| `.env.example` | Зразок налаштувань: доступ до моделі, параметри генерації, бюджет токенів |
| `check_env.py` | Перевірка середовища: Python, пакети, `.env`, пробний запит зі схемою відповіді |
| `context.md` | Правила організації — ті самі, що в ПР3, плюс формат номера замовлення |
| `compare/` | Порівняння трьох конфігурацій і класифікація помилок |

```
app/
├─ main.py                веб-рівень: сторінка і JSON-ендпоінт /api/chat
├─ llm.py                 модуль роботи з моделлю — заготовки функцій
├─ schema.py              контракт відповіді помічника — заготовка
└─ templates/index.html   сторінка діалогу з карткою звернення
```

Каркас дає структуру проєкту й робочий веб-рівень: сторінка веде розмову, надсилає нове повідомлення разом з історією і показує відповідь, картку звернення та службові дані. **Реалізації в ньому немає:** функції в `llm.py` і `schema.py` підіймають `NotImplementedError`, а ендпоінт не обробляє помилок.

## Початок роботи

```bash
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
copy .env.example .env
python check_env.py
```

Для macOS і Linux активація середовища — `source .venv/bin/activate`, копіювання — `cp .env.example .env`.

Ключ доступу той самий, що в ПР3, — можна скопіювати готовий `.env` із папки `pr3` замість `.env.example`. Тоді допишіть до нього рядки, яких там немає: тут зʼявилося налаштування `LLM_TOKEN_BUDGET`. Файл `.env` потрібен у кожній папці роботи окремо й до репозиторію не потрапляє.

**Запустіть `check_env.py` заздалегідь.** Крім пакетів і налаштувань він надсилає пробний запит **зі схемою відповіді** й показує, чи приймає провайдер `response_format`, скільки тривала відповідь і скільки токенів пішло. Якщо провайдер схему відхилив, скрипт скаже про це — тоді JSON доведеться просити текстом і розбирати самим.

Запуск застосунку з папки `pr4`:

```bash
uvicorn app.main:app --reload
```

Далі відкрийте http://127.0.0.1:8000 — сторінка вже працює, а сам запит завершиться помилкою, доки ви не реалізуєте модулі роботи з моделлю і схеми.

## Що очікує сторінка

Сторінка надсилає `POST /api/chat` з обʼєктом `{"message": "...", "history": [...]}`. Історія — це те, що сторінка вже показала: репліки клієнта і **текст** відповідей помічника (не весь JSON), кожна як `{"role": "user" | "assistant", "content": "..."}`.

У відповідь сторінка очікує `{"result": {...}, "model": "...", "elapsed": 1.23, "usage": {"prompt_tokens": ..., "completion_tokens": ...}}`, де `result` — перевірена за схемою відповідь моделі. Текст для клієнта сторінка бере з `result.reply`, решту полів `result` показує як картку звернення. Якщо назвете поля інакше — змініть сторінку, вона ваша.

Чи довіряти історії, яку надіслала сторінка, чи вести власну на сервері — рішення з розділу 2 практичної роботи. Каркас лише передає її далі.

## Що реалізувати

| Де | Що зробити |
|---|---|
| `app/schema.py` → `output_schema` | Спроєктувати схему відповіді: які поля потрібні програмі, які обовʼязкові, які з переліком значень |
| `app/schema.py` → `validate` | Перевірити сиру відповідь моделі за схемою й повернути дані, яким можна довіряти структурно |
| `app/llm.py` → `get_client` | Як у ПР3: клієнт створюється один раз |
| `app/llm.py` → `build_messages` | Скласти запит: інструкція з обмеженнями й прикладами, правила, історія, звернення — окремими частинами |
| `app/llm.py` → `estimate_tokens`, `fit_budget` | Оцінити розмір запиту і вмістити історію в бюджет: що відкидати першим, що не відкидати ніколи |
| `app/llm.py` → `ask` | Виклик, перевірка відповіді, поведінка при невалідній відповіді, час і `usage` |
| `app/main.py` → `api_chat` | Перенести обробку збоїв із ПР3 і додати новий: невалідна відповідь моделі |
| `compare/` | Три конфігурації на зверненнях і діалогах, класифікація помилок, висновки |

Рішення, які стоять за кожним пунктом, перелічені в розділі 2 практичної роботи — продумайте їх до того, як писати код.

## Чекліст самоперевірки

- [ ] Історія розмови передається моделі; факт із початку розмови використовується наприкінці без перепитування.
- [ ] Системна інструкція містить роль, обмеження, опис результату і приклади межових випадків.
- [ ] Інструкція, правила й текст клієнта — окремі частини запиту.
- [ ] JSON Schema відповіді є в коді; результат перевіряється програмно до того, як потрапить до веб-рівня.
- [ ] Невалідна відповідь не доходить до клієнта як є; факт записано в журнал.
- [ ] Історія вміщується в бюджет токенів із конфігурації; правило скорочення ви можете пояснити.
- [ ] Сторінка показує відповідь, картку звернення, модель, час і токени.
- [ ] Правила читаються з `context.md`; поза ними помічник не вигадує.
- [ ] Оброблено таймаут, перевищення лімітів, недоступність сервісу, помилку автентифікації.
- [ ] Ви вирішили, чи довіряти історії від клієнта, і можете пояснити наслідки.
- [ ] Ключ не потрапив ані в код, ані в репозиторій.
- [ ] Порівняння трьох конфігурацій проведено на 5–7 зверненнях і 2 діалогах; помилки класифіковано; висновки записано.
- [ ] Ви можете пояснити кожне ухвалене рішення.
