# Порівняння конфігурацій і класифікація помилок

У ПР3 ви порівнювали дві конфігурації однієї й тієї самої інструкції. Тут
порівнюються **три способи керувати моделлю** на тих самих зверненнях — і
збираються помилки, які кожен зі способів пропускає.

## Що зробити

1. Скопіюйте `requests.example.json` у `requests.json`. Перенесіть у нього
   свої 5–7 звернень із ПР3 і доповніть двома діалогами по 3–4 репліки
   (приклади — у файлі).
2. Прожене весь набір за трьох конфігурацій — по черзі, не змінюючи нічого
   іншого:
   - **нечіткий запит** — текст клієнта з інструкцією в один рядок; без
     формату, правил та історії;
   - **структурований prompt** — повна інструкція з обмеженнями, форматом
     і прикладами; без правил магазину та без історії;
   - **context engineering** — та сама інструкція плюс правила з
     `context.md`, історія в межах бюджету, перевірка за схемою.
3. Зафіксуйте результати кожного прогону.
4. Зберіть невдалі відповіді разом, класифікуйте їх і запишіть висновки у
   `findings.md`.

Як перемикати конфігурації — ваше рішення: змінна середовища, три варіанти
збирання запиту, окремий скрипт, що викликає модуль без веб-рівня. Останній
заощадить час: набір проганяється тричі, а діалоги — по репліці.

Діалог проганяють **послідовно**: кожна наступна репліка йде з історією
попередніх. У конфігураціях без історії кожна репліка йде окремо — саме так
видно, що втрачається.

## Що фіксувати

Для кожного звернення (і кожної репліки діалогу) в кожній конфігурації:

| Що | Навіщо |
|---|---|
| Чи відповідь пройшла схему | форма: без цього решту полів нема з чого читати |
| Чи тему визначено правильно | семантика: помилка тут надішле звернення не в той відділ |
| Чи вигадала модель факт | ґрунтованість: чи відповідь узято з правил, чи «з голови» |
| Що сталося на питанні поза правилами | відмова, здогадка чи вигадка |
| Чи згадала факт із початку діалогу | памʼять: чи спрацювала історія і чи не відрізало його скороченням |
| Токени запиту й відповіді (`usage`) | ціна конфігурації; порівняйте з власною оцінкою |
| Час виконання | чи можна чекати синхронно |

У нечіткій конфігурації схеми немає — фіксуйте, чи взагалі можна з відповіді
програмно щось узяти.

## Класифікація помилок

Усі невдалі відповіді з усіх прогонів зведіть в одну таблицю за типами з
розділу 1 практичної роботи:

| Тип | Приклад | Що ловить у вашому рішенні | Що не ловить |
|---|---|---|---|
| Синтаксична | відповідь не JSON; зайве поле | | |
| Семантична | тема поза переліком; номер, якого клієнт не називав | | |
| Фактична | вигадане правило | | |
| Контекстна | «забула» номер після скорочення історії | | |
| Поведінкова | змінила роль на вимогу клієнта; відповіла не тією мовою | | |

Стовпці «що ловить» і «що не ловить» — головні: це і є висновок про межі
вашого рішення.

## Що написати у висновках

Не переказ таблиць, а відповіді на питання:

- Що дала структура (перехід 1 → 2) і що дав контекст (перехід 2 → 3)? Що з
  цього змінило форму відповіді, а що — її зміст?
- Де модель позначила відповідь як ґрунтовану на правилах, хоча правил не
  бачила? Що це каже про довіру до полів, які заповнює сама модель?
- Який тип помилок лишився після всіх запобіжників? Що б ви додали наступним?
- Скільки коштує в токенах історія і скільки — правила? Де межа, після якої
  бюджет треба скорочувати?

`requests.json` і `findings.md` до репозиторію не потрапляють — вони ваші.
